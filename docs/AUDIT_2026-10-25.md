# Audit: 2026-10-25

Read-only audit by four reviewers: code review, security, web performance, test gaps and ship readiness. Nothing was changed in code.

**How far to trust this.** Findings come from reading the code. No test suite, Lighthouse run, `pip-audit` or `npm audit` was executed. Three items were re-checked by hand against the source (A1, A3, B1). Everything else is the reviewer's reading and should be confirmed before it is fixed. Performance items are potential impact, not measurements.

**Verdict: no-go for real patients today.** There are no critical vulnerabilities, but there are three correctness bugs on the emergency and money paths, one spoofable-IP issue that weakens login protection, and several ship blockers in operations.

## C. Reliability (code review, medium)

- C1. Cancelled or requeued rides never notify the hospital or driver (`ride_service.py:288-293, 306-311`, `dispatch_loop.py:113-127`). The first hospital stays alerted, and a driver keeps driving after a cancel.
- C2. A driver can cancel after pickup. The ride is marked cancelled with no requeue and the patient is stranded (`ride_service.py:312-315`).
- C3. The "call 1122" expiry message is one fire-and-forget push. Errors are swallowed and dead tokens are not pruned (`notifications.py:66-67, 119-124`, `dispatch_loop.py:84-92`). Add an SMS fallback.
- C4. The dispatch loop is serial, up to 20 rides at once, each up to about 15s. The `SKIP LOCKED` lock is released before dispatch runs, so two workers can dispatch the same ride (guarded UPDATEs keep it safe, but triage is duplicated). The docstring claim is wrong (`dispatch_loop.py:172, 196-203`).
- C5. The driver WebSocket never re-checks ride ownership after connect, so a replaced driver can keep publishing GPS (`ws.py:228-232`).
- C6. The watcher relay opens a DB session per GPS frame per watcher, which can exhaust the pool at 5 Hz (`ws.py:380-383`). Completion sets a driver `available` unconditionally, so a driver who went offline mid-ride becomes dispatchable (`ride_service.py:280-285`).

Checked and fine: commission charged exactly once, ride-state race guards, JWT decoding, SSRF defences on the FHIR POST, emergency-ride idempotency.

## D. Ship blockers (operations)

1. No alert delivery. There is no Alertmanager and only 4 rules. Nothing covers Redis or DB down, a stuck dispatch loop, aged pending rides, failed SMS/FHIR/push, or a ledger mismatch.
2. No backend deploy or rollback pipeline. `release.yml` builds only the APK and runs on any `v*.*.*` tag without waiting for CI.
3. RUNBOOK rollback is stale. Migration 0008 runs `DROP TABLE`, so a downgrade to 0005 passes through it.
4. `entrypoint.sh` runs `alembic upgrade head` on every start with no advisory lock, so two instances can race.
5. `render.yaml` uses the free plan for web and database (spins down when idle). Triage is not deployed. No Firebase variables.
6. Prod compose has a read-only root filesystem and no mount for `FIREBASE_CREDENTIALS_PATH`, so push silently no-ops.
7. `/health` checks nothing. Point orchestrator checks at `/ready`.
8. The RUNBOOK owner checklist is entirely open (domain, TLS, Firebase, Twilio, keystore, privacy policy and PHI review, hospital agreements, pen test, load test, real-phone testing). The e2e, dashboard, triage, security and Trivy jobs are listed as "written but never run".

Non-blockers: `.env.example` documents about 20 variables while `config.py` has many more (`SENTRY_DSN`, `ENVIRONMENT`, `FIREBASE_CREDENTIALS_PATH`, `DISPATCH_*`, `FARE_*`, `COMMISSION_RATE`, `LOGIN_*`, `SESSION_MAX_DAYS`, and others). No backup schedule.

## E. Test gaps (by risk)

1. Driver money screens (`top_up`, `wallet`, `earnings`, about 1,100 lines): no tests. RUNBOOK says drivers cannot top up themselves, but a 534-line top-up screen exists. Docs and code disagree.
2. Driver dispatch UI (`dashboard_screen.dart`, `dashboard_notifier.dart`, `active_ride_screen.dart`): only `heartbeat_test.dart`. Missing: accept a ride already taken (409), offline mid-ride, status transitions.
3. `notifications.py`: push, FHIR bundle build and post (timeout, redirect, 5xx) untested. The hospital pre-alert is the core promise.
4. `ride_service.py`: covered only indirectly. Missing illegal transitions, commission once under retry, refund on cancel, low wallet.
5. `emergency_dispatch.py`: garbage triage output, no hospital in range, hospital alert fails after driver assigned.
6. Live-tracking screen under reconnect and dropped socket.
7. `patient_service.py`, `hospital_service.py`: no direct tests (PHI ownership rules).
8. `ride_export.py`, `idempotency.py`: key reuse with different payloads, same-key races, export PHI scoping.
9. Dashboard e2e: no spec for driver verification, top-up retry, or admin cancelling a dispatching ride.
10. Patient app: about 40 screens, 14 test files, no integration tests, no Flutter coverage floor.

Strong areas: auth and security (11 files), dispatch races and resilience, wallet ledger, Redis resilience, SSRF.

## F. Dashboard performance (static, unmeasured)

- High: the app renders nothing on the server behind the auth gate, so LCP waits on hydration plus an API call (`components/AppShell.tsx:18-25`). Every route is dynamic because of `connection()` for the CSP nonce (`app/layout.tsx:20`). Recharts is imported eagerly on the analytics page (`app/analytics/page.tsx:6-9`). The dashboard skeleton does not match the real layout, so CLS is likely above 0.1 (`app/page.tsx:20-27, 70`).
- Medium: `ilike('%term%')` search with no trigram index (`ride_service.py:563`, `driver_service.py:159-164`, `patient_service.py:47-50`). `/summary` runs 7 scalar subqueries and is polled every 30s per open tab, and polling does not pause when the tab is hidden (`analytics.py:52-73`, `useApiData.ts:40-44`).
- Low: minor render costs. No images or custom fonts, so no font or LCP-image risk.
- Next step: run `/webperf` with a Lighthouse capture on `/` and `/analytics` to confirm.
